# 具体求解方案

## 0. 这份文档是干什么的

这份文档不是一页“快速上手”。它的目标更像是一份把项目掰开揉碎的学习手册。

你现在面对的不是一个只有几份脚本的小仓库，而是一个把以下几件事串在一起的项目：

1. 用 PowerShell 做外层调度。
2. 用 Java 写 COMSOL 模型模板。
3. 用 COMSOL 批处理编译并求解，得到 `.mph`。
4. 用 MATLAB 连接 `.mph`，继续做数据导出、绘图、汇总、测试。
5. 最后把结果写进统一的 `outputs/` 目录结构。

如果你只是想“跑一下”，你只需要记住几条入口命令。

如果你是想“真正学会整个项目”，你必须同时弄清楚两条主线：

- 第一条主线：项目架构。也就是仓库里有哪些目录、哪些文件、每个文件到底负责什么。
- 第二条主线：建模流程。也就是从哪一个入口开始，怎么一步一步经过 PowerShell、Java、COMSOL、manifest、MATLAB，最后落成 CSV、PNG、summary。

这份文档会同时完成这两件事。

## 2. 项目先看什么

如果你第一次接触这个仓库，我建议你先把它理解成一个三段式系统：

```text
你下命令
  ->
PowerShell 入口脚本
  ->
读取 params.json
  ->
scripts/comsol_common.ps1 统一补齐质量档位、路径、manifest/status 逻辑
  ->
把参数塞进 Java 模板
  ->
comsolcompile.exe 编译 Java
  ->
comsolbatch.exe 执行 .class
  ->
生成 .mph + shell 日志 + MATLAB handoff manifest/status
  ->
MATLAB 活动会话执行 run_matlab_manifest(...)
  ->
main_*_from_manifest.m
  ->
main_*.m
  ->
run_beam_model_pipeline.m 或 nonlinear 主函数
  ->
写出 CSV / PNG / summary.json / summary.txt / run_manifest.txt
  ->
outputs/
```

### 2.1 你应该先知道的最核心事实

这个仓库当前的正式约定不是“PowerShell 直接把 MATLAB 全部跑完”。

当前正式约定是：

- PowerShell 和 COMSOL 负责构建、求解、生成 `.mph`、布置输出目录、写 handoff 清单。
- MATLAB 不再被仓库脚本用 `matlab.exe -batch` 当作正式后端直接拉起。
- MATLAB 阶段需要在活动的 `VSCode + Codex Desktop + MATLAB extension` 会话中继续执行。

这意味着你看到 `scripts/run_matlab_model.ps1` 时，不要把它理解成“MATLAB 启动器”。它在这个仓库里的真实角色是：

- 写清楚 manifest/status/log stub。
- 告诉你 MATLAB 应该从哪里接手。

### 2.2 目录之间怎么配合

最简单的理解方式如下：

- `models/`：模型层入口。这里决定“我要跑哪个模型”。
- `scripts/`：共享调度层。这里放路径解析、质量档位、manifest/status、测试壳层、清理工具。
- `matlab/`：后处理层。这里真正把 `.mph` 转成可分析的数据和图。
- `outputs/`：正式结果层。这里放你最终要看的 summary、CSV、PNG、tables。
- `runtime/`：运行时隔离层，已清理；后续运行会重新生成 COMSOL 的临时 home/config/tmp/prefs/data。
- 历史 `archive/`：已删除。当前主线以 `models/`、`scripts/`、`matlab/` 和 `outputs/` 为准。

### 3.4 `scripts/`

#### `scripts/comsol_common.ps1`

- 文件类型：共享 PowerShell 工具库。
- 它做什么：这是整个 shell 层最核心的公共底座，负责路径解析、COMSOL/MATLAB 可执行文件定位、COMSOL runtime 隔离目录创建、外部程序调用、JSON 和 UTF-8 文件写入、manifest/status 文件写入、质量档位注入、输出根目录归档、模型清理辅助等一大批公共逻辑。
- 它通常被谁调用：几乎所有 `models/*/run.ps1`、`models/*/clean.ps1`、`scripts/run_all_tests.ps1`、`scripts/run_matlab_model.ps1` 都会引用它。
- 它会产出什么或影响什么：直接影响整个仓库的运行契约。你可以把它理解成“shell 主流程的标准库”。
- 重点理解：
  - `Get-LinearQualityProfile` / `New-ResolvedLinearConfig` 会把 `coarse / medium / full` 档位注入时间步、网格数和采样点。
  - `New-CodexMatlabHandoffManifest` / `Write-CodexMatlabStatusFile` 负责把 shell 阶段交给 MATLAB 的桥接信息写清楚。
  - `Initialize-CanonicalOutputRoot` 负责把旧结果归档到 `outputs/history/...`，保证当前输出根目录保持“规范 bundle”状态。
  - `Invoke-TsrModelClean` 负责清理模型输出和 runtime。

## 4. 建模主线一：单次线性求解怎么跑

这一章最重要。你如果只想真正掌握项目怎么从“命令”变成“结果”，这一章要精读。

### 4.1 推荐入口

我建议你先从总入口理解，而不是一上来钻到单个子目录里。

推荐先跑这几条 build-only 命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\models\linear\run.ps1 -Model base -Quality coarse -SkipMatlabPostprocess
powershell -ExecutionPolicy Bypass -File .\models\linear\run.ps1 -Model impact_response -Quality coarse -SkipMatlabPostprocess
powershell -ExecutionPolicy Bypass -File .\models\linear\run.ps1 -Model acoustic_field -Quality coarse -SkipMatlabPostprocess
```

为什么我推荐你先加 `-SkipMatlabPostprocess`？

因为这样最容易把职责分界看清楚：

- shell 负责做到哪里；
- MATLAB 接下来从哪里接手。

### 4.2 对应的 MATLAB continuation

```matlab
run_matlab_manifest('C:/Users/OMEN.LAPTOP-8C8PH934/code/cupt/the_singing_ruler/outputs/linear/base/logs/linear_base_matlab_manifest.json')
```

### 4.3 从命令到结果的完整 12 步

下面我把单次线性求解完整拆开。

#### 第 1 步：PowerShell 入口选模型

你先运行 `models/linear/run.ps1`，它根据 `-Model` 判断到底是去：

- `models/linear/base/run.ps1`
- `models/linear/impact_response/run.ps1`
- `models/linear/acoustic_field/run.ps1`
- `models/linear/app/run.ps1`

如果你传的是 `ALL`，它会依次分发。

#### 第 2 步：读取 `config/params.json`

每个子模型都有自己的默认配置：

- `models/linear/base/config/params.json`
- `models/linear/impact_response/config/params.json`
- `models/linear/acoustic_field/config/params.json`

这里面放的是默认几何、材料、激励、时间步、空气域参数。

#### 第 3 步：`scripts/comsol_common.ps1` 注入质量档位

子模型 `run.ps1` 会调用共享工具函数：

- `Get-LinearQualityProfile`
- `New-ResolvedLinearConfig`

它会根据 `coarse / medium / full` 自动修改：

- `mesh_numelem`
- `mode_points`
- `time_end`
- `time_step`

然后把修正后的完整配置写成：

- `outputs/linear/<model>/params_resolved.json`

这一步的意义是：你以后看结果，不要只看原始 `config/params.json`，更要看最终实际生效的 `params_resolved.json`。

#### 第 4 步：把参数块塞进 Java 模板

每个线性模型的 `run.ps1` 都会：

1. 读取 Java 模板。
2. 把 `__LINEAR_PARAM_BLOCK__` 替换成一串 `model.param().set(...)`。
3. 把生成后的 Java 放进：

```text
models/<...>/artifacts/build/run_<timestamp>/generated/
```

这一步很关键，因为仓库里 `src/*.java` 是模板，不是最终执行版。

#### 第 5 步：`comsolcompile.exe` 编译 Java

接着 shell 会调用 COMSOL 编译器，把生成后的 Java 编译成 `.class`。

结果会进入 `artifacts/build/run_<timestamp>/`。

#### 第 6 步：`comsolbatch.exe` 执行 `.class`

编译成功后，shell 用 `comsolbatch.exe` 跑这个 `.class`。

这时 Java 模板里定义的 COMSOL 模型树真正被执行：

- 创建 `Model`
- 建几何
- 建物理场
- 建网格
- 建 studies
- 运行 `std1` 和 `std2`
- 保存 `.mph`

得到的关键 shell 产物有：

- `mph/*.mph`
- `logs/*.log`

#### 第 7 步：写 MATLAB handoff manifest/status

求解完 `.mph` 以后，`run.ps1` 不会直接把后处理做完，而是写：

- `logs/*_matlab_manifest.json`
- `logs/*_matlab_status.json`

manifest 里最重要的信息包括：

- MATLAB 应该执行哪个入口函数
- `.mph` 在哪里
- 输出根目录在哪里
- 日志写到哪里
- 配置路径在哪里

#### 第 8 步：PowerShell 把任务正式交给 MATLAB

这一步由 `scripts/run_matlab_model.ps1` 完成。

但请注意，它不是帮你自动启动 MATLAB，而是：

- 检查环境
- 写 stub log
- 把状态设置成 `pending`
- 明确告诉你下一步该去 MATLAB 里执行 `run_matlab_manifest(...)`

#### 第 9 步：MATLAB 执行 `run_matlab_manifest(...)`

进入活动 MATLAB 会话后，真正的入口是：

```matlab
run_matlab_manifest('<manifest_path>')
```

这个函数会做这些事：

- 读 manifest
- 补 MATLAB 路径
- 切换到仓库根目录
- 打开 diary log
- 把状态从 `pending` 改成 `running`
- 根据 manifest 里的 `entry_function` 决定调用谁

#### 第 10 步：`main_*_from_manifest.m` 负责翻译 manifest

比如：

- `main_linear_base_from_manifest.m`
- `main_linear_impact_response_from_manifest.m`
- `main_linear_acoustic_field_from_manifest.m`

这些 wrapper 不做复杂计算，它们的任务是：

- 从 manifest 把字符串字段取出来；
- 变成真正的函数实参；
- 调用对应 `main_*` 主函数。

#### 第 11 步：`main_*` 主函数调用 `run_beam_model_pipeline.m`

线性三条单次主线中，真正的 MATLAB 核心都在：

- `main_linear_base.m`
- `main_linear_impact_response.m`
- `main_linear_acoustic_field.m`

其中最核心的公共流水线函数是：

- `matlab/core/run_beam_model_pipeline.m`

这个函数会：

1. 连接 `.mph`
2. 必要时检查 `sol1 / sol2` 是否存在
3. 必要时补跑 `std1 / std2`
4. 创建标准结果节点
5. 提取频率表
6. 提取自由端位移时程
7. 提取模态形状
8. 如果是 acoustic 场景，再提取麦克风声压时程
9. 写 CSV
10. 画 PNG
11. 保存 `.mph`

#### 第 12 步：写出最终 bundle

最后由：

- `write_output_metadata.m`
- 或 `publish_output_bundle.m`

把根目录 metadata 写齐：

- `summary.json`
- `summary.txt`
- `run_manifest.txt`

这时这个模型的正式输出 bundle 才算完整。

### 4.4 三个线性模型到底差在哪

#### `base`

`base` 是最基础的梁本体模型。

它的关注点是：

- 固有频率
- 自由端位移时程
- 模态形状

可以把它理解成“结构骨架”。

#### `impact_response`

`impact_response` 和 `base` 的核心差别是加入了冲击位置 `x0`。

也就是说，它不是只关心“理想末端受激”，而是关心“梁上某个位置受到短时冲击之后，结构如何响应”。

它依然还是结构主线，没有进入声压导出。

#### `acoustic_field`

`acoustic_field` 是在线性结构响应基础上，再向“能听见什么”推进一步。

它除了保留结构量：

- `frequencies.csv`
- `tip_timeseries.csv`
- `mode_shapes.csv`

还会再导出：

- `mic_pressure_timeseries.csv`
- `mic_pressure_fft.csv`
- `q_estimate.json`

以及对应的麦克风域图像。

所以如果你想学“这个项目的完整主链”，最终必须回到 `acoustic_field`。

### 4.5 求解模型的具体细节：参数、COMSOL 接口和可复建步骤

前面讲的是“流程怎么跑”。这一节换成“模型怎么搭”。
目标很明确：你只看这一节，应该能够知道当前仓库里三条线性模型到底使用哪些参数、这些参数从哪里来、在 COMSOL 里对应哪些接口、GUI 里应该建哪些节点，以及哪些内容其实不是 COMSOL 求解树，而是 MATLAB 后处理。

这一节以当前源码为准，尤其以这几类文件为准：

- `models/linear/base/config/params.json`
- `models/linear/impact_response/config/params.json`
- `models/linear/acoustic_field/config/params.json`
- `models/linear/*/src/*.java`
- `models/linear/*/run.ps1`
- `scripts/comsol_common.ps1`
- `matlab/main_linear_acoustic_field.m`

#### 4.5.1 先记住参数生效顺序

这个项目不是直接把 Java 模板顶部那几行默认参数当成最终参数来跑。
真正的参数生效顺序是：

```text
config/params.json
  -> scripts/comsol_common.ps1 里的 Quality profile
  -> outputs/.../params_resolved.json
  -> run.ps1 生成 __LINEAR_PARAM_BLOCK__
  -> artifacts/build/.../generated/*.java
  -> comsolcompile.exe
  -> comsolbatch.exe
  -> .mph
```

这句话非常重要。原因是 Java 模板里会有一些兜底初值，例如 `rho = 7850[kg/m^3]`、`E = 200e9[Pa]`、`nu = 0.30`、`J = 0.02[N*s]`。这些值不是当前正式运行口径。正式运行时，`run.ps1` 会把 `params.json` 和 `Quality` 档位合成最终配置，再把最终参数重新注入 Java 的 `// __LINEAR_PARAM_BLOCK__` 位置。

所以你手工搭 COMSOL 时，应按下面这个优先级取值：

1. 先看本节列出的“当前默认生效值”。
2. 如果你指定了 `-Quality coarse` 或 `-Quality medium`，再用 Quality 覆盖表替换 `mesh_numelem`、`time_end`、`time_step`、`mode_points`。
3. 如果你已经实际跑过一次，以 `outputs/.../params_resolved.json` 为最终事实。
4. 不要把 Java 模板顶部的兜底参数误当成最终研究参数。

参数也分三类：

- 原始输入参数：来自 `params.json`，例如 `L_free`、`b`、`h`、`rho`、`E`、`J`。
- COMSOL 求解参数：会进入 Java 模型树，例如 `mesh_numelem`、`time_end`、`time_step`、`eigen_modes`。
- MATLAB-only 参数：不进入 COMSOL 求解树，例如 `mode_points`，它控制模态形状导出时的采样点数。

#### 4.5.2 Quality 覆盖表：不同档位真正改了什么

`Quality` 不是一个只写在日志里的标签，它会实际覆盖时间窗、时间步、网格数量和 MATLAB 模态采样点。当前源码里的覆盖表如下。

| 模型 | Quality | `mesh_numelem` | `mode_points` | `time_end` | `time_step` |
|---|---:|---:|---:|---:|---:|
| `base` | `full` | `120` | `241` | `1[s]` | `1e-4[s]` |
| `base` | `medium` | `90` | `161` | `0.5[s]` | `2e-4[s]` |
| `base` | `coarse` | `40` | `61` | `0.10[s]` | `1e-3[s]` |
| `impact_response` | `full` | `160` | `241` | `1[s]` | `1e-4[s]` |
| `impact_response` | `medium` | `120` | `161` | `0.5[s]` | `2e-4[s]` |
| `impact_response` | `coarse` | `50` | `61` | `0.10[s]` | `1e-3[s]` |
| `acoustic_field` | `full` | `160` | `241` | `1[s]` | `1e-4[s]` |
| `acoustic_field` | `medium` | `120` | `161` | `0.5[s]` | `2e-4[s]` |
| `acoustic_field` | `coarse` | `50` | `61` | `0.10[s]` | `1e-3[s]` |

这里要分清楚：

- `mesh_numelem` 进入 COMSOL 网格节点 `mesh1/edg1/dis1`。
- `time_end` 和 `time_step` 进入 COMSOL 瞬态 study 的 `tlist`。
- `mode_points` 不进入 Java 模型树；它被 MATLAB 后处理用来决定 `mode_shapes.csv` 里沿梁长度取多少个采样点。

如果你要“先快速搭通”，建议按 `coarse` 理解；如果你要“按默认研究口径复建”，则按 `full` 理解，因为各 `run.ps1` 的默认 `Quality` 是 `full`。

#### 4.5.3 三条线性模型的共同物理假设

`base`、`impact_response`、`acoustic_field` 三条线性主线共享同一个结构骨架：

- 结构形式：Euler-Bernoulli 梁。
- COMSOL 物理接口：Structural Mechanics 里的梁接口，对应 Java 类型 `HermitianBeam`。
- 几何形式：不是 3D 实体块，而是 3D 几何空间中的 1D 梁轴线。
- 根部边界：理想固支，对应 `Fixed`。
- 自由端：不施加约束。
- 激励形式：短时冲击点载荷，对应 `PointLoad`。
- 研究步骤：先 `Eigenfrequency`，再 `Transient`。
- 主要输出：固有频率、自由端位移时程、模态形状。

这套假设适合解释细长尺子的一阶到低阶弯曲振动，也适合解释短时冲击后的瞬态衰减。它当前不适合直接解释完整三维实体夹持、接触、塑性、强几何非线性或全空间高保真声辐射。

#### 4.5.4 `base` 模型参数表

`base` 是最小结构基线。它的默认参数来自 `models/linear/base/config/params.json`，再叠加 `Quality` 覆盖。

| 参数名 | 当前默认生效值 | 来源 | COMSOL 用途 | 备注 |
|---|---:|---|---|---|
| `L_total` | `0.30[m]` | `geometry.L_total` | 记录总尺长 | 当前几何轴线实际用 `L_free` |
| `L_free` | `0.18[m]` | `geometry.L_free` | 梁轴线长度 | Java 内部设 `L = L_free` |
| `b` | `0.03[m]` | `geometry.b` | 矩形截面宽度 | 写入 `csd1.hy_rect` |
| `h` | `0.001[m]` | `geometry.h` | 矩形截面厚度 | 注入 Java 后改名为 `h_beam`，写入 `csd1.hz_rect` |
| `rho` | `7930[kg/m^3]` | `material.rho` | 梁材料密度 | 写入 `beam/emm1.rho` |
| `E` | `193e9[Pa]` | `material.E` | 杨氏模量 | 写入 `beam/emm1.E` |
| `nu` | `0.29` | `material.nu` | 泊松比 | 写入 `beam/emm1.nu` |
| `root` | `ideal_clamp` | `boundary.root` | 语义标记 | 实际 COMSOL 节点是 `Fixed` |
| `tip` | `free` | `boundary.tip` | 语义标记 | 自由端不创建约束节点 |
| `excitation_mode` | `impact` | `excitation.mode` | 语义标记 | 当前 Java 实际用冲击点载荷 |
| `use_impulse` | `1` | `excitation.use_impulse` | 冲击开关 | 进入 `Fimp` 表达式 |
| `J` | `0.002[N*s]` | `excitation.J` | 冲量 | 进入 `Fimp` 表达式 |
| `tau_imp` | `2e-4[s]` | `excitation.tau_imp` | 脉冲宽度 | 进入 `t_imp` 和 `Fimp` |
| `pulse_shape` | `square_like` | `excitation.pulse_shape` | 语义标记 | 当前实际表达式是高斯型短脉冲 |
| `eigen_modes` | `6` | `studies.eigen_modes` | 特征频率阶数 | 写入 `std1/eig.neigs` |
| `time_end` | `1[s]` | `studies.time_end` + Quality | 瞬态终止时间 | 写入 `std2/time.tlist` |
| `time_step` | `1e-4[s]` | `studies.time_step` + Quality | 瞬态时间步 | 写入 `std2/time.tlist` |
| `mesh_numelem` | `120` at `full` | Quality | 梁单元数量 | 写入 `mesh1/edg1/dis1.numelem` |
| `mode_points` | `241` at `full` | Quality | 不进 COMSOL | MATLAB 导出模态形状时使用 |

手工搭 `base` 时，最少要把这些量填进 COMSOL 参数表：

```text
L_total = 0.30[m]
L_free = 0.18[m]
L = L_free
b = 0.03[m]
h_beam = 0.001[m]
rho = 7930[kg/m^3]
E = 193e9[Pa]
nu = 0.29
use_impulse = 1
J = 0.002[N*s]
tau_imp = 2e-4[s]
t_imp = 5*tau_imp
Fimp = use_impulse*J/(tau_imp*sqrt(pi))*exp(-((t-t_imp)^2)/(tau_imp^2))
eigen_modes = 6
time_end = 1[s]
time_step = 1e-4[s]
mesh_numelem = 120
```

如果按 `coarse` 快速搭建，把最后三项换成：

```text
time_end = 0.10[s]
time_step = 1e-3[s]
mesh_numelem = 40
```

#### 4.5.5 `base` 的 COMSOL GUI 构建树和 Java API 对照

`base` 的模型树可以按下面顺序搭。左边是你在 COMSOL GUI 里应该理解的节点，右边是源码里的 Java API 类型和 tag。

| GUI/模型树含义 | Java tag / 类型 | 关键设置 |

#### 4.5.6 `impact_response` 的参数和构建差异

`impact_response` 不是另起炉灶，它是在 `base` 梁模型上把冲击位置显式放进几何点表。新增的核心参数是：

| 参数名 | 当前默认生效值 | 来源 | COMSOL 用途 | 备注 |
|---|---:|---|---|---|
| `x0` | `0.75*L_free` | `excitation.x0` | 几何中间点、点载荷位置 | 直接进入 `pol1` 点表 |
| `mesh_numelem` | `160` at `full` | Quality | 两段梁边的分布网格 | `coarse` 时为 `50` |
| `mode_points` | `241` at `full` | Quality | 不进 COMSOL | MATLAB-only |

其余几何、材料、边界、冲击参数与 `base` 相同，仍然是：

```text
L_total = 0.30[m]
L_free = 0.18[m]
L = L_free
b = 0.03[m]
h_beam = 0.001[m]
rho = 7930[kg/m^3]
E = 193e9[Pa]
nu = 0.29
x0 = 0.75*L_free
J = 0.002[N*s]
tau_imp = 2e-4[s]
eigen_modes = 6
time_end = 1[s]
```

载荷 tag 从 `pl1` 换成 `plimp`，并施加在选择号 `2` 上：

网格要覆盖两段边：

- 点载荷选中的是中间点 `x0`，不是自由端。
- 网格边选择要包含两段 `{1,2}`，否则后一段可能没有按预期分布网格。

#### 4.5.7 `acoustic_field` 的参数和源码真实边界

`acoustic_field` 在 COMSOL 侧继承 `impact_response` 的结构梁模型。也就是说，它仍然是：

```text
Transient study
```

它额外带入了声学后处理参数：

| 参数名 | 当前默认生效值 | 来源 | COMSOL 用途 | 当前真实作用 |
|---|---:|---|---|---|
| `initial_tip_displacement` | `0[m]` | `excitation.initial_tip_displacement` | 参数表保留 | 当前主要求解仍由冲击载荷驱动 |
| `use_air_domain` | `true` -> Java 中为 `1` | `acoustics.use_air_domain` | 参数表保留 | MATLAB `mic_expr` 开关 |
| `air_radius` | `0.5[m]` | `acoustics.air_radius` | 参数表保留 | 当前 Java 未显式创建空气域 |
| `mic_distance` | `0.06[m]` | `acoustics.mic_distance` | 参数表保留 | MATLAB 声压表达式分母距离 |
| `rho_air` | `1.225[kg/m^3]` | `acoustics.rho_air` | 参数表保留 | MATLAB 声压表达式系数 |
| `c_air` | `343[m/s]` | `acoustics.c_air` | 参数表保留 | 当前主要作为声学参数记录 |
| `mesh_numelem` | `160` at `full` | Quality | 两段梁边网格 | `coarse` 时为 `50` |
| `mode_points` | `241` at `full` | Quality | 不进 COMSOL | MATLAB-only |

手工搭 `acoustic_field` 的 COMSOL 结构树时，可以先完全照 `impact_response` 搭。然后在参数表里额外加入：

```text
initial_tip_displacement = 0[m]
use_air_domain = 1
air_radius = 0.5[m]
mic_distance = 0.06[m]
rho_air = 1.225[kg/m^3]
c_air = 343[m/s]
A = b*h_beam
I = b*h_beam^3/12
```

但是这里必须明确一件事：当前 Java 源码没有显式创建完整空气声学有限元模型树。也就是说，当前 Java 里没有这些 COMSOL 节点：

- 没有 `Pressure Acoustics` 物理场。
- 没有空气球域或空气盒子几何。
- 没有空气域材料分配。
- 没有空气域网格。
- 没有声硬边界、辐射边界、PML 或远场声学边界。
- 没有结构-声学强耦合边界条件。

`models/linear/acoustic_field/config/params.json` 里的 `modules: ["Structural Mechanics", "Acoustics"]` 表示这条路线面向声学输出，但不等于当前 Java 已经搭完完整声学 FEM。

当前麦克风压力由 MATLAB 后处理表达式导出。表达式在 `matlab/main_linear_acoustic_field.m` 中是：

```text
if(use_air_domain,rho_air*A/(4*pi*mic_distance)*d(d(w,t),t),0[Pa])
```

拆开看就是：

- `w` 是梁横向位移。
- `d(d(w,t),t)` 是梁横向加速度。
- `rho_air*A` 给出与空气密度和等效面积相关的缩放。
- `4*pi*mic_distance` 给出简化空间辐射衰减。
- `use_air_domain` 是开关，为假时返回 `0[Pa]`。

所以 `acoustic_field` 当前真实链路是：

```text
COMSOL 梁瞬态响应 w(t)
  -> MATLAB 通过 mic_expr 抽取等效声压
  -> mic_pressure_timeseries.csv
  -> mic_pressure_fft.csv
  -> SPL / RMS / peak-to-peak / Q estimate
```

#### 4.5.8 Java 内部派生参数

下面这些量不一定直接写在 `params.json` 里，但构建 COMSOL 模型时必须存在：

| 派生参数 | 表达式 | 使用位置 |
|---|---|---|
| `L` | `L_free` | 梁轴线终点 |
| `h_beam` | `h` | COMSOL 参数名不能直接和其他上下文混淆，Java 注入时改名 |
| `A` | `b*h_beam` | `acoustic_field` 的声压后处理表达式 |
| `I` | `b*h_beam^3/12` | 梁截面二次矩记录，目前主要用于参数完整性 |
| `t_imp` | `5*tau_imp` | 冲击脉冲中心时刻 |
| `Fimp` | `use_impulse*J/(tau_imp*sqrt(pi))*exp(-((t-t_imp)^2)/(tau_imp^2))` | `PointLoad.forcePoint` 的 z 向载荷 |

注意 `Fimp` 虽然看起来像力，但它是一个随时间变化的表达式。它的幅值由冲量 `J` 和脉冲宽度 `tau_imp` 共同决定。

| `t_end_s` | `1.0` | 仿真终止时间 |
| `dt_s` | `1.0e-4` | 输出时间步 |

实际求解的 ODE 是：

```text
x' = v
v' = -2*zeta*omega0*v - omega0^2*x - alpha3*x^3
omega0 = 2*pi*f1_hz
```

它输出：

- `tables/response_timeseries.csv`
- `tables/response_fft.csv`
- `figures/large_amplitude_response.png`
- `figures/large_amplitude_fft.png`
- `summary.json`

所以这条线是在“线性 COMSOL 梁模型已经给出参考频率”的基础上，解释大振幅下可能出现的频率偏移和非线性响应，不是替代前三条 COMSOL 构建链。

#### 4.5.15 最小验收清单：照文档搭完后怎么检查

搭 `base` 后检查：

- 参数表里有 `L_free`、`b`、`h_beam`、`rho`、`E`、`nu`、`J`、`tau_imp`、`Fimp`。
- 几何是两个点一条边。
- 根部点固定。
- 自由端点有 `PointLoad`。
- 网格只有一条边，元素数为 `mesh_numelem`。
- 有 `Eigenfrequency` 和 `Transient` 两个 study。
- `Eigenfrequency` 不带点载荷。

搭 `impact_response` 后检查：

- 参数表额外有 `x0`。
- 几何是三个点两条边。
- 固定端是 `x=0`。
- 点载荷在 `x=x0`。
- 自由端 `x=L` 没有固定。
- 网格覆盖两条边。
- `Eigenfrequency` 禁用的是 `plimp`。

搭 `acoustic_field` 后检查：

- COMSOL 侧结构树与 `impact_response` 基本一致。
- 参数表额外有 `use_air_domain`、`mic_distance`、`rho_air`、`c_air`。
- 不应该凭当前源码期待看到完整空气域 physics 树。
- 麦克风声压、FFT、SPL、Q 估计要到 MATLAB 后处理里看。

如果你的目标是“照这节直接复建当前项目”，那么验收标准不是“搭出最复杂的声学模型”，而是“搭出和当前源码等价的结构求解树，并清楚知道 MATLAB 接手声学后处理的位置”。

## 5. 建模主线二：声学扫参与 sweep 怎么跑

### 5.1 入口命令

build-only：

```powershell
powershell -ExecutionPolicy Bypass -File .\models\linear\acoustic_field\sweep.ps1 -Mode frequency_scan -Quality coarse -SkipMatlabPostprocess
powershell -ExecutionPolicy Bypass -File .\models\linear\acoustic_field\sweep.ps1 -Mode ALL -Quality coarse -SkipMatlabPostprocess
```

MATLAB continuation：

```matlab
run_matlab_manifest('C:/Users/OMEN.LAPTOP-8C8PH934/code/cupt/the_singing_ruler/outputs/sweeps/linear/acoustic_field/<sweep_id>/logs/sweep_matlab_manifest.json')
```

### 5.2 sweep 不是什么

sweep 不是“一个更大的单模型”。

sweep 的真实含义是：

- 先批量构造许多 case；
- 每个 case 都是一次完整的 `acoustic_field` 单次运行；
- 最后再在 sweep 根目录上做汇总。

### 5.3 shell 端具体做了什么

`models/linear/acoustic_field/sweep.ps1` 会这样做：

1. 读取基础配置 `models/linear/acoustic_field/config/params.json`。
2. 如果是 `impulse_waveform` 模式，就改写 `J`。
3. 如果是 `frequency_scan` 模式，就改写 `L_free` 和 `h`。
4. 为每个 case 创建：
   - case 目录
   - case 专属 runtime 目录
   - `params_case.json`
5. 对每个 case 调一次 `models/linear/acoustic_field/run.ps1`。
6. 收集每个 case 的路径、`.mph` 路径、summary 预期位置、麦克风 CSV 预期位置。
7. 写 sweep 根目录：
   - `sweep_manifest.json`
   - `summary.json`
   - `run_manifest.txt`
   - `logs/sweep_matlab_manifest.json`
   - `logs/sweep_matlab_status.json`

### 5.4 MATLAB 端具体做了什么

在 MATLAB 里真正接手的是：

- `main_linear_acoustic_field_sweep_postprocess_from_manifest.m`
- `main_linear_acoustic_field_sweep_postprocess.m`

它会：

1. 遍历每个 case。
2. 对每个 case 调一次 `main_linear_acoustic_field(...)`。
3. 把 case 的 `summary_path`、`mic_csv_path` 等字段写回 manifest。
4. 调用 `main_linear_acoustic_field_sweeps.m`。
5. 由聚合函数在 sweep 根目录生成 summary 图和 summary 表。

### 5.5 sweep 根目录和 case 目录的区别

#### sweep 根目录

你要把它理解成“总览层”。

典型文件有：

- `summary.json`
- `run_manifest.txt`
- `sweep_manifest.json`
- `figures/` 下的汇总图
- `tables/` 下的汇总表
- `logs/` 下的 handoff 文件和 MATLAB 日志

#### case 目录

你要把它理解成“单次 bundle 层”。

每个 `cases/<case_id>/` 里面仍然是一个完整单次 acoustic bundle：

- `params_resolved.json`
- `summary.json`
- `summary.txt`
- `run_manifest.txt`
- `mph/`
- `logs/`
- `data/`
- `figures/`

也就是说：sweep 不是替代单次 bundle，而是“批量生成许多个单次 bundle，再做一层汇总”。

### 6.2 这条线和 COMSOL 主线的关系

5. 对响应做 FFT。
6. 写：

## 11. 一句话收尾：你现在应该怎样理解整个项目

如果把整个仓库压缩成一句话，可以这样理解：

这个项目的核心不是“某一个 Java 文件”或者“某一个 MATLAB 文件”，而是一条分工非常清楚的流水线：

- `models/*/run.ps1` 决定跑谁；
- `scripts/comsol_common.ps1` 负责统一壳层规则；
- `src/*.java` 负责搭 COMSOL 模型树；
- COMSOL 负责把模型解出来，变成 `.mph`；
- `run_matlab_manifest.m` 负责接住 handoff；
- `main_*.m` 和 `run_beam_model_pipeline.m` 负责把 `.mph` 变成真正能分析的 CSV、PNG 和 summary；
- `outputs/` 则是你最终交付和复盘的地方。

只要你把这条链真正看顺了，这个项目就不再是“很多文件”，而是一套非常清楚的求解系统。
